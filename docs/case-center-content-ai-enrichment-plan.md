# 案例中心全量内容优化与 AI 生图技术方案

> 日期：2026-08-05
> 状态：待评审（数据盘点基于本地开发库 `tzj_dev`，为生产快照恢复，结论以生产复核为准）
> 范围：`apps/api`（Case 数据与发布）、`apps/web`（案例列表/详情 C 端）、AI 生图资产与 OSS 上传
> 关联：`docs/web-seo-assessment-and-plan.md`（案例详情 SEO 基线）、
> `docs/web-image-loading-optimization.md`（OSS 图片处理管线）、
> `AGENTS.md`（生产数据唯一权威 `REDACTED-IP`，禁止直接改生产库）

## 结论先行

案例中心目前 52 条数据中只有 **3 条标杆案例**（河南某省消防总队训练基地、广东某支队 CFBT 训练中心、
山西某矿山救援队训练设施）完成了「深度文案 + AI 实景图」级别的优化，其余约 **48 条**大多是
早期迁移的模板内容：描述为通用公司文案、无亮点/无规格参数、封面为占位图。

本方案给出可批量复制的执行框架：

1. **先盘点后生产**：先完成全量案例清单、重复项合并与内容质量分层（阶段 A），避免在重复/废数据上重复做工。
2. **内容包标准化**：每案例按固定「内容包」生产（摘要 + 800~1200 字 Markdown 正文 + 4~6 条亮点 + 6~8 条规格 + SEO 字段），LLM 辅助初稿、人工审定。
3. **AI 生图标准化**：统一风格基准与提示词模板；**每案例所有图片必须是同一建筑的不同视角/内部视角**
   （封面为基准锚点，其余视角基于锚点生成），走现有 OSS 压缩管线。
4. **详情页画廊本期不做，但图集照常生成**：每案例生成 1 张实拍级封面 + 1 张详情页宽幅封面
   （约 3:1，独立生图不与封面共用）+ 3~4 张多视角图集图，全部上传 OSS 并回填
   `coverImage/detailCoverImage/images[]`；图集以**正文内嵌方式**展示（见 3.8），
   详情页独立画廊待功能恢复后再升级。
5. **分批发布 + 验收门禁**：按 `caseType` 分 6 批推进，每批有量化验收标准，达标才发布。

### 1.3 现状问题

1. **内容质量断层**：`caseshow-*` 描述为「河南拓之迹实业有限公司，专业拓展器材生产厂家……」的通用模板，
   同一文案出现在几十条案例中，既无项目信息也无 SEO 价值，还会稀释全站可信度。
2. **重复/近似项目**：如「新疆某部训练基地 / 训练场 / 基地」多条、「洛阳部队场地 / 心理行为训练场」多条，
   存在同一项目重复入库或近似项目，直接逐条重做会浪费产能（见阶段 A 去重）。
3. **图集字段暂不展示（本期不做画廊）**：`Case.images[]` 已有数据但 C 端详情页只渲染 `coverImage`；
   图集照常生成入库，画廊展示后续另行立项。
4. **规格参数缺失**：`caseshow-*` 全部无 `specs`，侧栏「项目信息」空白；细节规格恰是工业客户决策的关键信息。
5. **SEO 字段空置**：多数案例无 `seoTitle/seoDesc`，详情页 metadata 退化为从 summary 兜底，
   与 `docs/web-seo-assessment-and-plan.md` 的 SEO 基线不一致。

### 1.4 数据模型与语言范围

**本方案只做中文（zh-CN）**：

- `Case` 现有单语言字段即够用，**不需要任何 schema 变更**，后台录入与 C 端展示链路零改动；
- en / zh-TW 等其它语言页面暂沿用中文内容，不属于本方案范围（后续如要做，再单独立项扩展 `CaseI18n`）；
- 文案与 SEO 字段一律按中文质量基线生产。

## 二、目标与原则

### 2.1 目标

- 全部发布案例（除已达标标杆）达到「内容完整 + AI 封面完整 + SEO 完整」的标杆级质量。
- 案例中心成为 C 端可信的工程能力证明，而非公司简介堆砌。
- 过程可批量、可复核；生产数据变更按后台常规审计留痕。

### 2.2 原则

| 原则 | 说明 |
|---|---|
| 真实优先，无需脱敏 | 新文案**不需要脱敏**（不要求匿名化），按既有事实口径书写；不编造信息、不虚构敏感参数 |
| AI 图实拍级 | 生成图以「实拍级工业摄影」为标准（无 AI 味），与文案参数一致；含人员时仅允许远景无正脸 |
| 无水印 | 生成图一律**不添加水印/角标/署名**（品牌水印也不需要），保持实拍照片观感 |
| 不碰涉密信息 | 部队/公安/消防类项目不出现营区布局、安防细节、精确坐标等敏感信息 |
| 先合并后生产 | 重复/近似项目先由业务确认合并策略，再进入内容生产，避免浪费 |
| 事实有出处 | 每个参数（层数/燃烧室/工期/地点/完成时间）必须有来源：后台历史数据、合同/竣工资料或客户确认；无法确认的留空不编 |
| 以现有描述为锚 | 内容与生图必须以该案例**现有字段**为基准（title/summary/specs/client/location/completionDate），只扩写补全，绝不改写既有事实口径 |
| 数据走正规通道 | 生产数据只通过后台管理端或审批过的脚本修改，禁止直连生产库手改 |

## 三、内容规范（每案例「内容包」）

### 3.1 字段级标准

| 字段 | 要求 | 示例 |
|---|---|---|
| `title` | 设施类型，20 字内（无需脱敏） | 某市公安特警攀登训练楼 |
| `slug` | 英文 kebab，稳定后不改 | `shandong-police` |
| `summary` | 一句话（背景 + 建设内容 + 价值），60~100 字 | 见标杆 |
| `description` | Markdown，800~1200 字，固定章节 | 见 3.2 |
| `highlights` | 4~6 条，每条含量化信息 | 「7 层固定训练塔，含电梯井与楼梯塔」 |
| `specs` | 6~8 项（塔型/层数/燃烧室/结构/抗风/工期/交付/地点） | 见标杆 |
| `coverImage` | AI 封面 16:9，OSS key | `content/case-{slug}-hero.png` |
| `detailCoverImage` | AI 详情页宽幅封面（约 3:1，**独立生图，不与封面共用**）；**俯视图全景航拍：合适的俯视角度（约 45°~60°），完整呈现建筑顶面与场地全貌**，OSS key | `content/case-{slug}-detail-hero.png` |
| `images[]` | 3~4 张 AI 图集 4:3（画廊暂不展示，先入库） | `content/case-{slug}-gallery-{n}.png` |
| `location` / `client` | 省份 / 客户（按既有口径，无需脱敏） | 河南 / 某省消防救援总队 |
| `completionDate` | 确切的年份-月；不确则填年份 | 2023-06 |
| `seoTitle` / `seoDesc` | 含案例类型 + 地域关键词，60/120 字内 | — |
| `caseType` | 保持现有枚举 | fire/police/… |

> **扩写红线**：`client / location / completionDate / specs / summary 中的设施构成` 一律以现有记录为锚，
> 扩写只能增加细节与表述，不得改客户、地点、时间，不得改变设施类型与数量。
> **无需脱敏**：新文案不做匿名化处理，按既有事实口径书写。

### 3.2 描述正文章节模板（Markdown）

```text
## 项目背景
（客户类型、训练需求、场地/预算约束，2~3 句，不虚构具体单位）

## 建设方案
（设施组成：塔型/燃烧室/辅助系统；布局思路；与训练科目的对应关系）

## 核心亮点
（承接 highlights，展开为 3~4 段，每段一个能力点 + 数据支撑）

## 交付与服务
（交钥匙流程、验收培训、售后/扩展能力）

## 项目价值
（对客户训练体系的提升，1~2 段收尾）
```

#### 3.2.1 排版与间距规范（参考业内最佳实践）

生成文案时必须遵守 Markdown 排版规范，**杜绝标题与上文紧贴**（如「项目背景」紧跟在段落
末尾无空行，渲染后会挤在一起）：

| 规则 | 要求 |
|---|---|
| 标题前后空行 | 每个 `##`/`###` 标题前后都必须有**空行**（`\n\n`），标题与上/下文至少一个空行间隔 |
| 标题层级 | 小节用 `##`，子项用 `###`；禁止用 `**加粗**` 代替标题，禁止 `####` 以上深层级 |
| 段落间距 | 段与段之间空行；列表项之间不空行，列表前后各留一个空行 |
| 图文间距 | 正文内嵌图片前后各留一个空行；图片不紧贴标题/段落，避免图文粘连 |
| 正文可读性 | 段落单段 3~5 行内，避免超长段落；数字/参数用列表或表格承载，不用大段文字堆砌 |
| 渲染兜底 | 页面由 `MarkdownBody` 渲染（`@tzj/ui`）；已修复「首标题 `first:mt-0` 导致紧贴上文」的问题，`##`/`###` 标题上边距统一生效（mt-10/mt-8），内容源遵守上述规则即可获得统一美观间距 |

**正反例（生成时必须按正例）**：

```text
❌ 反例：标题紧贴上文（上一行不是空行）
……为高校安全工程相关专业建设实训教育基地。
## 项目背景
某理工大学需要……

✅ 正例：标题前后都有空行
……为高校安全工程相关专业建设实训教育基地。

## 项目背景

某理工大学需要……
```

校验脚本（阶段 B）增加排版断言：**标题上一行必须是空行（紧贴上文即失败）**、
无 `**标题**` 伪标题、段落间空行数量正确；验收阶段对详情页做一次人工视觉检查
（标题/段落/图文间距）。

### 3.3 规格模板（按 caseType 适配）

| caseType | 必填规格 |
|---|---|
| fire / police / military | 塔型、层数、燃烧室/训练场景、结构、抗风设计、工期、交付模式、地点 |
| scenic / school | 塔型、高度/层数、功能组合、安全配置、工期、交付模式 |
| enterprise | 塔型、模块数、功能、安全配置、工期、交付模式 |

### 3.4 语言范围

- 全部内容（标题/摘要/正文/亮点/规格/SEO 字段）只做**中文（zh-CN）**；
- 不引入翻译流程、不扩展数据模型、不增加多语言录入成本；
- 如未来需要英文/繁体，另行立项（届时需 `CaseI18n` 子表 + 后台按语言编辑 + API 按 locale 返回）。

### 3.5 事实来源与核对（每个案例必填）

内容生产前先建立「事实清单」，逐案例一栏：

| 字段 | 来源（至少其一） | 无法确认时 |
|---|---|---|
| location / client | 后台历史数据 / 合同 / 客户确认 | 留空，不猜地名 |
| completionDate | 合同或验收记录 | 只填年份，甚至留空 |
| specs（层数/燃烧室/工期等） | 合同/竣工资料/现场照片 | 该规格不写，宁缺毋滥 |
| 项目亮点 | 现场照片/客户反馈/工程记录 | 用可验证的能力描述，不编数据 |

核对流程：内容包初稿 → 事实清单标注每项来源 → 业务确认人逐项打勾 → 才允许进入生图与发布。
任何「看起来合理但无出处」的参数一律不写入（AI 图参数同样以此清单为准）。

### 3.6 锚点字段示例（以 `jiangsu-university` 为例）

生成文案与生图前，先从现有记录提取以下锚点，**不得偏离**：

| 锚点 | 值（现有描述） |
|---|---|
| 标题 | 某高校安全实训教育基地 |
| 客户 | 某理工大学 |
| 位置 | 江苏 |
| 完成时间 | 2022-09-01 |
| 设施构成 | 紧凑标准固定塔 + 教学友好型低强度燃烧模块 + 开放式训练平台 |
| 用途 | 教学演示、课程实训 |

- 扩写正文时围绕「高校安全工程专业、教学演示与课程实训」展开，不出现消防支队/实战化等与锚点冲突的表述；
- 生图时画面必须是「校园环境中的紧凑标准训练塔 + 教学型燃烧模块 + 开放平台」，而非消防大队训练基地。

### 3.7 封面更新与缓存（实验注意事项）

- **封面来源**：列表页取 `coverImage`；详情页 Hero 优先 `detailCoverImage`（独立宽幅），
  未设置时回退 `coverImage`；两者均由 API 下发，更新后对应位置变化；
- **web 端 GET 缓存 `revalidate: 60`**：更新 DB 后列表/详情最多延迟 60s 生效；实验验证时
  等 60s 或强制刷新（`Cmd/Ctrl+Shift+R`），不要一改就判定「没生效」；
- **next/image / 浏览器缓存**：封面 URL 变化后按新 URL 加载，旧 URL 的缓存不影响新封面；
- **禁止用静态 `apps/web/src/lib/cases.ts` 改列表封面**：该文件只服务快捷入口/静态资源清单，
  不是案例列表数据源（列表页走 API）；改它不会让 `/cases` 封面变化，也会与 DB 数据分叉。

### 3.8 正文内嵌图集（本期图集展示形式）

详情页独立画廊本期不做，**图集图以内嵌方式展示在正文 Markdown 中**（复用现有
`MarkdownBody` → `MediaImage` 链路，天然获得 next/image 优化、懒加载与 OSS 压缩）：

| 项 | 要求 |
|---|---|
| 插入方式 | 在 `description` 中按顺序插入 `![alt](图片URL)`，图片前后各留空行（遵守 3.2.1） |
| 数量与顺序 | 每案例正文内嵌 ≥ 3 张：外景全景 → 另一外景角度 → 近景结构 →（可选）内部视角 |
| 位置建议 | 「建设方案」段后插 1 张全景，「核心亮点」段内按亮点配 1~2 张，文末插内部视角收尾 |
| alt 规范 | `{案例标题} · {视角说明}（{序号}/{总数}）`，如「某矿山救援队训练设施 · 竖井模拟单元（2/4）」 |
| 与 images[] 一致 | 内嵌图片 URL 必须与 `images[]` 同源同集合（先回填 images[]，再从其中选图内嵌） |
| 图床 | 一律走 OSS key（`content/case-{slug}-gallery-{n}.png`），禁止外链图床 |
| 详情封面不内嵌 | `detailCoverImage` 只用于详情页 Hero，不参与正文内嵌 |

> 这样画廊功能恢复后，无需返工：`images[]` 已完整入库，正文内嵌与未来画廊可并存。

## 四、AI 生图规范

### 4.1 产出与规格

> 本期范围：**每案例生成 1 张实拍级封面 + 1 张详情页宽幅封面 + 3~4 张多视角图集图**
> （按 4.2.2/4.2.3 执行），全部上传 OSS 并回填 `coverImage/detailCoverImage/images[]`；
> 图集图以**正文内嵌方式**展示（见 3.8），
> 详情页独立画廊本期不开发，画廊功能恢复后可升级。

| 用途 | 数量 | 比例 | 最低尺寸 | 输出格式 | 视角建议 |
|---|---|---|---|---|---|
| 封面（hero） | 1 张/案例 | 16:9 | 1920×1080 | PNG/WebP（上传管线转 WebP q80） | 全景主视角（基准锚点，完整展示建筑轮廓） |
| 详情页封面（detail hero） | 1 张/案例 | 约 3:1 宽幅 | 1920×640 | 同上 | **俯视图全景航拍**：合适的俯视角度（约 45°~60°），完整呈现建筑顶面、轮廓与四周场地；不过度垂直（避免只剩屋顶平面）、不过低（避免底部裁切）；**顶部预留安全区**（详情页 Hero 顶部会被固定导航遮挡，主体不得顶到画面顶端）；同一建筑宽幅构图（可由封面锚点派生），不与其他图共用 |
| 图集（gallery） | 3~4 张/案例 | 4:3 | 1600×1200 | 同上 | 另一外景角度 / 近景结构 / 内部视角 |

### 4.2 同一建筑一致性（硬性要求）

> **铁律：一个案例 = 一栋建筑。** 案例内所有图片必须能被用户明确识别为
> 「同一个设施」，只能通过机位、景别、视角变化呈现，严禁出现两栋不同结构/
> 颜色/场地的建筑混在一个案例里（这是「一眼假」的主要来源）。

#### 4.2.1 建筑身份表（Building Identity Sheet）

每案例生图前先冻结一份身份表，所有图片共享同一份特征：

| 特征 | 说明 |
|---|---|
| 塔型/结构 | 固定塔 / 模块塔 / 燃烧室，层数、轮廓、洞口与开窗布局 |
| 材质与涂装 | 镀锌钢本色 + 品牌红点缀，护栏/平台样式 |
| 旧图标语文字 | 若旧图可见文字（如塔身「严格训练」），记录原文并入身份表；新图**尽量复现同一文字**（提示词逐字指定，审核确认无错字/乱码） |
| 场地特征 | 训练地面材质、围栏、周边参照物（山体/厂房/树木） |
| 光照与天空 | 同一时段与天空方向（如「晨昏多云、太阳在左侧」），避免同案例出现正午+黄昏混用 |
| 摄影风格 | 焦段、饱和度、锐度统一（见 4.2.3 视角模板） |
| 文案锚点 | 设施构成/数量/用途取自该案例现有 summary+specs（如 `jiangsu-university` 的「紧凑标准固定塔 + 教学型低强度燃烧模块 + 开放平台」），生图画面必须与锚点一致 |

#### 4.2.2 生成方法（必须基于锚点，禁止纯文本重 roll）

1. 先生成并审核通过 1 张**全景主视角**作为基准锚点（即封面）；
2. 其余外景/近景/内部视角一律**以锚点图为参考图**（image reference / img2img）生成，
   提示词只改机位与景别（`same building, seen from the left side / entrance close-up /
   interior of the burn room`），不重 roll 建筑本体；
3. 不支持参考图的生图工具直接淘汰，不用；
4. 生成后逐张与锚点图比对（见 4.5 审核 checklist），不一致的淘汰重做。

#### 4.2.3 视角模板（每案例至少覆盖）

| 序号 | 视角 | 景别/焦段 | 作用 |
|---|---|---|---|
| 1 | 全景主视角（封面） | 24mm 广角 / 无人机航拍 | 建立建筑整体印象，作为锚点 |
| 2 | 另一外景角度 | 50mm 中焦，侧面或入口 | 证明「同一栋」的侧面轮廓 |
| 3 | 近景结构 | 85mm，楼梯/平台/钢构节点 | 展示工艺细节 |
| 4 | 内部视角（按 caseType） | 20mm 广角，燃烧室/通道/训练间 | 展示内部空间（消防/CFBT 必做） |

> 详情页宽幅封面（约 3:1）为第 1 项「全景主视角」的**宽幅远景派生**：机位拉远，
> **优先无人机俯视图全景**：机位在建筑上方，俯视角度约 45°~60°（**合适的俯视角度**），
> 完整纳入建筑顶面、轮廓与四周场地——不过度垂直（避免只剩屋顶平面）、不过低（避免底部裁切）；
> **顶部预留安全区**——详情页 Hero 顶部会被固定导航
> 遮挡，画面最上方约 1/4 保持天空/环境留白，主体下移不顶格；可由封面锚点派生构图，
> 禁止近景裁切主体、禁止另起建筑。

#### 4.2.4 禁止事项

- 同案例出现两栋不同结构/颜色/背景的建筑；
- 用不同案例的图拼进同一案例图集；
- 同案例内天空光照方向、季节、场地环境明显冲突；
- 仅靠「重 roll 随机出一张像的」替代参考图生成；
- **给生成图叠加水印/角标/署名（含品牌水印）**——生成、压缩、上传各环节均不得加水印。

#### 4.2.5 旧图处置策略（先判定，再生成）

生成前先盘点该案例现有 `coverImage / detailCoverImage / images[]`（本期画廊不做，
但图集照常生成入库；处置规则对封面、详情封面与图集一视同仁，现存脏数据顺带清理），按以下规则处置：

| 旧图状态 | 判定标准 | 处置 |
|---|---|---|
| ✅ 可用作参考 | 旧图与旧描述能对应（主体设施类型、场景、数量与 summary+specs 一致，如消防案例配的是消防训练塔实拍） | 保留旧图，作为**参考图/锚点**参与生成；能基于真实照片衍生视角时优先用它，比纯 AI 锚点更真实 |
| ❌ 作废删除 | 旧图与旧描述明显不符（如矿山救援案例配的是通用训练塔图、高校案例配的是消防大队基地图、占位图/其它案例复用图） | **彻底删除旧图**（DB 移除 `coverImage/images[]`，OSS 对象下线），完全依据旧描述重新生成，**不再参考旧图** |
| ⚪ 无图 | 原案例没有可用图片 | 直接按锚点字段生成，无参考图 |

判定时机：阶段 A 盘点时完成（逐案例标注「可用参考 / 作废删除 / 无图」），
避免生成阶段才返工；拿不准时按「与描述不符」从严处理（宁删勿混）。
旧图若含可见文字（标语/铭牌），无论是否作参考，先提取原文写入身份表（4.2.1），
新图尽量复现，避免「新图干净、旧图有字」的口径断裂。

> 实例：`shanxi-mine-rescue` 当前封面为通用塔图 `content/tower-eastside.jpg`，
> 与「矿山救援、地下巷道/竖井模拟」描述不符 → 按 ❌ 处置：删除旧图，按旧描述重新生成。

### 4.3 风格基准（与三条标杆一致）

- 写实工业摄影风格，环境光自然，中远景构图；
- 设施主体：镀锌钢训练塔 / 燃烧室 / 训练平台，红色品牌点缀；
- 背景：训练场、厂区或自然地形，天空中性（晨昏/多云），无夸张特效；
- 人员：仅允许远景训练剪影，禁止正脸、制服细节、单位标识；
- 画面内不得出现真实单位名称、Logo、车牌、地图坐标等可识别信息。

### 4.4 提示词模板（英文为佳，生成后按中文文案校对参数）

```text
Photorealistic industrial photograph of a galvanized steel fire training tower
{towerType: fixed 7-story with elevator shaft / modular training tower / burn room},
{surroundings: training ground / industrial yard / campus / scenic base},
neutral overcast sky, soft daylight, wide shot, {camera: 24mm / drone aerial},
no people in foreground, no text, no logos, no watermarks.
```

参数按案例 `specs` 反推（层数、模块数、燃烧室数量等必须与文案一致），
避免「图上 5 层、文案 7 层」的图文矛盾；场景与用途按现有 summary 设定
（如高校案例用校园环境 + 教学型设施，不用消防大队基地），
**先读锚点字段再写提示词，禁止凭想象换场景**。
若身份表含标语文字（如「严格训练」），提示词逐字写明并指定原文：
`wall slogan text "严格训练" rendered exactly, no typos`；中文文字易被 AI 生成出错，
**无法准确渲染时宁可不加文字，严禁出现错字/乱码**。

详情封面（detail hero）提示词单独指定：`top-down panorama aerial view at a suitable downward
angle (about 45-60 degrees), ultra-wide establishing shot, entire building roof layout, outline
and surrounding site fully in frame, not too vertical (avoid roof-only flat view), not too low
(avoid cropping the base), camera pulled back, generous empty margin in the top third of the frame,
building positioned lower in frame`——俯视图全景、合适的俯视角度（45°~60°）、机位拉远、
顶面/轮廓/场地完整入画、顶部 1/3 留白（固定导航遮挡区）。

### 4.5 生成与审核流程

1. 按内容包生成候选（每图 2~3 张候选）；
2. 自动初筛（尺寸/文件大小/格式）；
3. 审核 checklist：
   - [ ] 结构与文案参数一致（层数/模块数/配置）
   - [ ] 无文字伪影、无 Logo/水印/单位标识
   - [ ] 无水印/角标/署名（生成后不得后处理加水印）
   - [ ] 无正脸人员、无涉密/可识别场景
   - [ ] 品牌色调一致、无恐怖谷/明显 AI 痕迹
   - [ ] **与案例现有描述一致**：设施构成/数量/客户/地点/时间无冲突（对照 3.6 锚点字段）
   - [ ] **与锚点图为同一建筑**（轮廓/层数/颜色/场地/光照方向逐项比对）
   - [ ] **详情封面为俯视图全景**：俯视角度合适（45°~60°），建筑顶面、轮廓与场地完整入画，不过度垂直/不过低裁切
   - [ ] **顶部安全区充足**：画面顶端留白/天空，模拟固定导航遮挡后主体（含塔顶）仍完整可见
   - [ ] **旧图标语文字已尽量复现**且无错字/乱码（无法准确渲染时已省略，不留乱码）
   - [ ] 同案例图组互为可辨识的多视角，不出现第二栋建筑
   - [ ] 内部视角与外部视角结构呼应（如窗外护栏、墙体材质一致）
4. 通过后上传 OSS（key 规范见 4.6），入库前用 `next/image` 预览验证。

> **验证方式约定**：本方案**不使用 MCP/浏览器自动化**（Playwright、BrowserUse 等）打开浏览器
> 验证页面或图片；需要验证时一律用非浏览器方式——`curl` 检查 HTTP 状态与资源可访问、
> 检查渲染后的 HTML 输出、静态资源 HEAD/尺寸断言。不设置人工验证环节。

### 4.6 OSS 资源命名与压缩

- 建议 key：`content/case-{slug}-hero.png`、`content/case-{slug}-detail-hero.png`、
  `content/case-{slug}-gallery-{1..4}.png`
  （与标杆 `content/case-*-hero.png` 一致；或经后台上传走 `images/{YYYYMM}/` 亦可）；
- 上传复用现有图片压缩管线（`image-compression.ts`：WebP q80、最长边 2560、去 EXIF），
  单文件目标 < 500KB；C 端展示由 `oss-image-loader` 分级质量 + WebP 兜底；
- 封面沿用 `preload/eager`；图集懒加载策略待画廊功能落地后再定（预留）。

#### 4.6.1 阿里 OSS 不会自动压缩原图（重要前提）

- OSS 存储的是**上传时的原始字节**，存储侧不会自动压缩/缩放；
- 它的图片处理是**读取时按需**的：`x-oss-process=image/resize,w_xxx/quality,q_xx/format,webp`。
  生产环境 C 端已由 `oss-image-loader` 统一追加该参数（本项目已实现），浏览器拿到的是压缩派生图；
- 结论：必须**双管齐下**——上传前压缩（控制存储与源文件体积）+ 读取时处理（控制流量与首屏）。

#### 4.6.2 同步/上传前压缩门禁（硬性步骤）

- 任何进入 OSS 的生成图，必须先过压缩管线：WebP q80、最长边 2560、去 EXIF；
- 压缩后校验：单文件 < 500KB 且为 WebP，超限自动降质重压或拒绝入库；
- 批量同步（如 `ossutil sync` / 部署脚本）**禁止把生图目录原样同步**——必须先跑压缩脚本
  产出 `dist/` 再同步；后台手动上传沿用现有 StorageController 压缩逻辑（已实现）；
- 批次脚本加断言：`find dist -name '*.webp' -size +500k` 任一命中即失败。

### 4.7 工具选型、版权与成本

- 生图工具须满足三个条件：**支持参考图/图生图**（同一建筑多视角的前提）、**可商用授权**、
  产出可归档（不锁死在平台内）。当前环境可用的 Codex imagegen 支持基于参考图派生变体，可作默认工具；
  若批量产能不足，再评估即梦/可灵等国内工具，签约前先确认商用授权条款。
- 规模估算：约 48 案例 × 6 张（封面 + 详情封面 + 3~4 图集）≈ **288 张**，
  按每张 2~3 次生成 + 1 次审核 ≈ 700~900 次生成；
  单张 < 500KB WebP，总存储约 120MB，OSS 存储/流量成本可忽略。
- 资产归档：每案例保留「提示词 + 参数 + 锚点图 + 审核结论」到 `docs/ai-assets/` 或后台附件，
  便于复盘与复用风格。
- 实拍级标准：生成图必须达到「可直接放进官网当真实项目照片」的观感——光影、透视、结构比例、
  材质符合物理规律，无塑料感、对称伪影、异常重复纹理等典型 AI 痕迹（审核标准见 4.5）。

## 五、技术落地（分阶段）

### 阶段 A：盘点与去重（0.5~1 天）

- 输出全量案例清单（slug/标题/类型/状态/内容完整度/图片数），按类型分桶；
- 逐案例标注**旧图处置结论**（✅ 可作参考 / ❌ 作废删除 / ⚪ 无图），写入盘点表；
- 用「标题归一 + location + client 相似度」找出重复/近似组，产出**合并建议表**：
  - 同一项目多条记录 → 保留 1 条并合并图片，其余归档（`status=draft` 或删除需业务确认）；
  - 近似但独立项目 → 各自保留，内容生产时区分；
  - 草稿/无价值记录 → 建议下线清单；
- 合并决策由业务负责人确认后再执行（本阶段不写生产库）；
- **SEO 迁移**：被合并记录的旧 slug 不能直接 404——保留原记录改 draft 并做 301（或 Next 端 slug
  别名映射），sitemap 重新生成，避免收录与历史外链丢失；归档记录软删除而非物理删除。

### 阶段 B：内容生产（按 caseType 分 6 批）

- 每批先做 1 条「样板」并由业务确认，再批量铺开；
- LLM 辅助初稿（基于既有行业知识库/标杆文案），人工按 3.1/3.2 标准审定；
- 产出物直接通过后台管理端录入（`cases` 管理页），或由审批过的种子脚本批量写入；
- 每批完成后跑**内容校验脚本**（dry-run，只读）：
  - 完整性：desc ≥ 800、highlights ≥ 4、specs ≥ 6、cover + detailCoverImage + images ≥ 3、seo 字段齐全；
  - 模板残留：命中黑名单即失败（如「专业拓展器材生产厂家」「为广大客户」「河南拓之迹实业有限公司……」）；
  - 敏感词：部队番号、精确地址、手机号/座机、坐标等；
  - 排版：`##`/`###` 标题前后有空行、无 `**加粗**` 伪标题、段落间空行合规；
  - 内嵌图集：`description` 内图片数量 ≥ 3、图片 URL 与 `images[]` 一致、图片前后有空行；
  - 一致性：specs 参数与 AI 图事实清单可对照（人工复核项，脚本只标记差异）。

### 阶段 C：AI 生图

- 按 4.x 规范逐案例生成封面 + 详情封面 + 图集 → 审核 → 上传 OSS →
  回填 `coverImage/detailCoverImage/images[]` →
  按 3.8 在 `description` 中插入内嵌图集；
- 与阶段 B 并行（文案参数先冻结，图按参数生成）。

### 阶段 D：C 端增强（代码改动，A2 范围）

1. **详情页图集画廊：本期不做**（暂缓，避免 `images[]` 无处展示；预留「懒加载网格/灯箱/键盘操作」
   需求，待恢复时按此实现）；
2. **SEO/JSON-LD**：详情页 `articleJsonLd` 的 `image` 数组本期仅封面（图集数组预留），
   `description` 用 `seoDesc`；
3. **性能**：封面沿用 `preload/eager` + OSS 分级参数，详情页 LCP/CLS 不回退。

### 阶段 E：发布与验证

- 后台批量发布（`status=published` + `systemPublishedAt`）；
- 验证：案例列表/详情无 404、封面可加载、sitemap 收录新页面；
- 验证手段统一为非浏览器方式（curl / HTML 输出检查 / 静态资源断言），不开 MCP 浏览器自动化；
- 封面验证注意 3.7：更新后等待 60s 缓存或强刷，确认列表/详情两处封面一致；
- 抽查 + Lighthouse（LCP/CLS/INP）+ 全站 `pnpm run check` + typecheck 门禁。

## 六、验收标准（每条案例）

1. `description` ≥ 800 字且为结构化 Markdown，无「河南拓之迹实业有限公司，专业拓展器材……」模板残留；
2. `highlights` ≥ 4 条、`specs` ≥ 6 项，参数与 AI 图一致；
3. `coverImage` + `detailCoverImage` + `images[]` ≥ 3 张，全部通过 4.5 审核 checklist 并已入库 OSS
   （`detailCoverImage` 为独立宽幅封面，不与 `coverImage` 共用，且为**俯视图全景、
   俯视角度合适、顶面/轮廓/场地完整入画、顶部留白充足**（遮挡后主体仍完整）；
   画廊未做，先存后用）；
4. **同一建筑一致性**：以封面为锚点人工比对，案例内全部图片为同一建筑多视角
   （含至少 1 张内部视角，如适用），无「一案例多建筑」；
5. `seoTitle/seoDesc` 已填，详情页 metadata/OG/JSON-LD 输出正确；
6. 无需脱敏：新文案不做匿名化处理；不新增涉密/敏感参数；
7. 图片经压缩管线处理（WebP、单文件 < 500KB），C 端懒加载正常；
8. 重复项合并完成，案例中心无重复项目可见。
9. **事实核对通过**：事实清单每项有来源（历史数据/合同/客户确认），无来源参数未写入；
10. 内容校验脚本通过（完整性/模板残留/敏感词三项全绿），发布后详情页 200、封面可加载。
11. **排版美观**：详情页人工视觉检查通过——标题/段落/图文间距舒适，无标题紧贴上文、图文粘连。

## 八、风险与依赖

| 风险/依赖 | 影响 | 对策 |
|---|---|---|
| 重复项目合并需业务拍板 | 阶段 A 阻塞 | 盘点后输出合并建议表，一次评审会确认 |
| AI 图与真实交付不符 / 一眼假 | 客户信任风险 | 以「实拍级」标准生成与审核（4.3/4.5），图文参数一致；明显 AI 味一律重做 |
| 部队/公安类涉密边界 | 合规风险 | 敏感词/涉密检查清单，生图/文案双重人审（不要求匿名化，但不得新增涉密信息） |
| 生产数据写入 | 数据事故 | 只走后台/审批脚本；脚本需 dry-run + 备份；遵循 AGENTS.md 生产权威 |
| AI 生图风格漂移 | 视觉不统一 | 冻结风格基准与提示词模板；同案例图组同批生成 |
| AI 生图跨图不一致（一案例多建筑） | 用户一眼假、信任受损 | 基准锚点 + 参考图生成 + 逐图比对 checklist；不一致一律重做 |
| 事实数据不可得（无合同/记录） | 排期膨胀、参数缺失 | 阶段 A 先盘点「无来源案例」清单并让业务补资料；补不到的按 3.5 降级（不写该参数） |
| 合并后旧 URL 丢失 | 收录与历史外链受损 | 阶段 A 同步 301/别名映射 + sitemap 重建，发布前验证旧 slug 不 404 |
| AI 工具商用授权不明确 | 版权风险 | 生图工具选定前先确认可商用授权条款，资产归档留证 |
| `images[]` 历史脏数据 | 未来画廊上线时展示异常 | 阶段 A 顺带清洗 images[]（无效 key/重复图），为画廊预留干净数据 |
